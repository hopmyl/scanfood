## Сводка

**Архитектура:** Vite 7 + React 19 + TS strict + Tailwind 4 + Zustand 5 (persist, миграции) + React Router 7 + vite-plugin-pwa. Структура чистая и однообразная: `screens/` (7 экранов), `components/` (3), `store/` (1 стор), `lib/` (match/scan-client/utils), `data/` (25 файлов блюд). Никаких «временных» костылей в UI-слое, селекторы Zustand везде на примитивах, типобезопасность отличная: `strict`, ни одного `any`/`@ts-ignore`, только 5 оправданных `as unknown as` для `MediaTrackCapabilities.zoom` (нет в DOM-типах). `tsc --noEmit` — чисто.

**Данные — эталонно:** 399 блюд в исходниках (50 базовых в `dishes.ts` + 50 в `dishes-extra-a/b/c` + 299 кухонь мира), 260 с фото → в каталоге ровно 260 (161 ЛАЙТ + 99 PRO). Автопроверка скриптом: **0** дубликатов id, **0** битых ссылок фото (манифест ↔ `public/dishes` идеальный синк через `prebuild`), **0** мёртвых id в `PRO_DISH_IDS`/`WORLD_PRO_IDS`, **0** пересечений PRO-списков, **0** блюд без ingredients/steps/kcal/bju/category, все `image` каноничны (`/dishes/<id>.jpg`), `DISH_META` покрывает все блюда, КБЖУ сходится с формулой 4/4/9 (±30%, аномалий нет), дубликатов nameRu/nameEn нет. Единственная шероховатость данных — 46 ингредиентов в 36 блюдах без `qty` и без `note` (в основном смеси специй «Соль, перец, хлопья чили») — на UI не влияет, `qtyLine()` даёт пустую строку.

**Бандл:** `dist/assets/index-*.js` = 1,3 МБ (329 КБ gzip), один чанк, ни одного dynamic import. Раздуватели (по esbuild-metafile, до минификации): данные блюд ~1,0 МБ, @zxing ~1,1 МБ (статически), react/react-dom ~1,2 МБ dev-исчисление. Оценка: ленивая загрузка zxing срезает ~0,4–0,5 МБ minified (~120 КБ gzip), React.lazy экранов — ещё заметный кусок.

**Ключевые риски:** (1) публично скачиваемый архив исходников в `public/`, который деплоится на оба зеркала; (2) дизайн-решение шить `VITE_OPENROUTER_KEY` в публичный бандл зеркал; (3) сканер штрих-кодов не возобновляется после показа товара; (4) монолитный бандл без code-splitting.

**Счётчик находок:** 4 критичных · 10 важных · 14 некритичных/полировка · топ-10 быстрых побед. Всего 28 пунктов.

## КРИТИЧНО

### К1. Архив исходников лежит в `public/` и деплоится на оба зеркала
- **Где:** `public/skanrecept-src-2026-10-29.zip` (14,9 МБ, 161 файл) → копируется в `dist/` при каждой сборке (подтверждено: `dist/skanrecept-src-2026-10-29.zip` присутствует) → доступен любому по `https://hopmyl.github.io/skanrecept-src-2026-10-29.zip` и `…/scanfood/…`.
- **Суть:** внутри — весь `src/` (вся рецептурная база = главный актив проекта), скрипты генерации фото, и файл `.env` (проверено содержимое: только `DATABASE_URL=file:…` — локальная ссылка, не секрет; но при следующем обновлении архива туда легко попадёт настоящий ключ).
- **Почему важно:** полная утечка контента конкурентам, +15 МБ к каждому деплою и к обходам краулеров, риск случайно заархивировать реальный секрет.
- **Исправление:** `rm public/skanrecept-src-2026-10-29.zip dist/skanrecept-src-2026-10-29.zip`, перезадеплоить оба зеркала; добавить в `.gitignore` шаблон `public/*.zip`; если архив нужен для бэкапа — хранить вне `public/` (например, `download/` или облачное хранилище).

### К2. `VITE_OPENROUTER_KEY` шьётся в публичный бандл зеркал (по дизайну — но требует контроля)
- **Где:** `src/lib/scan-client.ts:276-283` (ключ читается из `import.meta.env`), `scripts/deploy-pages.sh:17`, `scripts/deploy-all.sh:14` (прокидывают `OPENROUTER_KEY` при сборке).
- **Проверка:** в текущем локальном `dist/assets/index-*.js` ключа **нет** (поиск `Bearer <token>` и `sk-or…` — пусто; присутствует только URL `openrouter.ai/api/v1/chat/completions` и заголовок `X-Title`). Т.е. локальная сборка чистая; риск появляется ровно в момент запуска `OPENROUTER_KEY=… deploy-pages.sh`.
- **Почему важно:** любой посетитель зеркала вытаскивает ключ из бандла; если ключ получит кредит или будет использован платный — списания не контролируемы. Код честно предупреждает (`scan-client.ts:11-13`, комментарий в deploy-скрипте), но технической защиты нет.
- **Исправление:** (а) держать на OpenRouter нулевой кредитный лимит и только `:free`-модели (уже заявлено — закрепить в чек-листе деплоя); (б) среднесрочно — не шить ключ, а оставить только `VITE_SCAN_API_URL` на внешний API с CORS (он уже есть в цепочке шагом выше и не требует секрета на клиенте); (в) ротировать ключ и следить за usage на дашборде OpenRouter.

### К3. Сканер штрих-кодов «умирает» после первого результата — замороженный видоискатель
- **Где:** `src/screens/ScanScreen.tsx:770` (`zxingRef.current?.stop()` в `handleBarcode`), строки 1372-1379 («Сканировать другой» — только `setProductState({kind:'idle'})`), 880-885 (`resetResult` — не трогает сканер). Эффект сканера запускается только по deps `[mode]` (строки 593-627).
- **Суть:** после первого найденного/ненайденного кода `controls.stop()` гасит и декодер, и видеотрек. `camState` остаётся `'on'` → UI показывает «живой» видоискатель с лазерной линией, но кадр заморожен и сканирование не идёт. Пользователь может продолжить только переключив режим «Продукты → Штрих-код» и обратно.
- **Почему важно:** основной сценарий «отсканировать несколько покупок подряд» сломан — это ядро barcode-фичи.
- **Исправление:** вынести запуск декодера в функцию `startBarcode()` и вызывать её из эффекта + после `resetResult` и кнопки «Сканировать другой» (или: не вызывать `stop()` в `handleBarcode`, а ставить флаг «обрабатываем» и возобновлять через `controls` в UI-кнопке «Сканировать другой»). Мини-вариант: в `resetResult`/«Сканировать другой» дергать перезапуск эффекта через `setBarcodeEpoch(e=>e+1)` и добавить `barcodeEpoch` в deps эффекта.

### К4. Цепочка скана может заставить ждать пользователя ~2 минуты до фолбэка
- **Где:** `src/lib/scan-client.ts:46-47` (`ENDPOINT_TIMEOUT = 55_000`, `DIRECT_TIMEOUT = 70_000`), шаги 1→2 (`tryScanEndpoint`) → 3 (OpenRouter).
- **Суть:** если задан `VITE_SCAN_API_URL` и он завис (не отвечает, чёрный ход через CORS-заглушку), клиент ждёт до 55 с на `/api/scan` + ещё до 55 с на внешний API, и только потом OpenRouter (70 с). Худший случай ≈ 180 с при одном таймауте «повесить и ждать». На GitHub Pages первый шаг падает мгновенно (405), это ок; проблема именно с живым, но тормозящим/зависшим внешним API.
- **Почему важно:** 1–2 минуты «Распознаём продукты…» на мобильном = пользователь уходит, плюс списанный скан висит всё это время.
- **Исправление:** дифференцировать таймауты: первый (same-origin) — 10–15 с (он либо мгновенно 404/405, либо это серверless с лимитом ~50 с — но тогда внешний API и есть серверless… компромисс: `VITE_SCAN_API_URL`-попытке дать 25–30 с, а same-origin 55 с); опционально — параллельный «гонка» с OpenRouter при наличии ключа (`Promise.any`), первый успех побеждает.

## ВАЖНО

### В1. Монолитный бандл 1,3 МБ: @zxing грузят все, данные блюд — одним куском
- **Где:** `src/screens/ScanScreen.tsx:3` — статический `import { BrowserMultiFormatReader } from '@zxing/browser'`; `src/data/dishes.ts:272-273, 1408-1410` — все 25 файлов данных импортируются статически; `src/App.tsx:4-10` — все 7 экранов импортированы статически.
- **Замеры (esbuild, minify):** полный бандл 1,84 МБ / 367 КБ gzip; без zxing 1,35 МБ / 241 КБ gzip → **zxing ≈ 0,49 МБ minified / ~126 КБ gzip** только ради barcode-режима. Данные блюд (25 файлов) ~1,0 МБ до минификации; после минификации в реальном vite-бандле это значимая доля 1,3 МБ.
- **Почему важно:** первый запуск на мобильном в РФ (часто слабая сеть) прямо упирается в этот JS; PWA-прекеш тоже кеширует весь монолит.
- **Исправление (по шагам):**
  1) barcode-эффект: `const { BrowserMultiFormatReader } = await import('@zxing/browser')` внутри `useEffect` — чанк отгрузится только при входе в режим «Штрих-код»;

  3) (опционально) вынести кухни мира в отдельный чанк: `const DISHES_WORLD = await import('./dishes-world')` в точке сборки `ALL_DISHES` — минус ~60% данных из стартового чанка; данные нужны и для матчинга, поэтому проще начать с 1)+2).
